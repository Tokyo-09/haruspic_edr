# Spire Setup: установка сервера и агентов

Первый установщик — интерактивный мастер в терминале. Один дистрибутив содержит
агент, сервер и инструменты проверки подписанных баз. В Windows мастер собирается
в `SpireSetup.exe`, Python на клиенте не нужен. На Linux запускается `install.sh`
(Python 3.10+). Сервер в обеих ОС устанавливает отдельный Python 3.12 и зависимости
из `server/uv.lock` через включённый `uv`; при первой установке сервера нужен интернет.
Агенту нужен только доступ к серверу и feed.

## Для клиента

Администратор выдаёт архив под ОС/архитектуру и файл `enrollment.json`.
Распакуйте архив в отдельную папку, профиль держите за её пределами. Не меняйте
содержимое дистрибутива: мастер проверяет его состав и SHA-256 файлов.

**Linux:** из распакованной папки выполните `sudo ./install.sh`.

**Windows:** запустите `SpireSetup.exe`, подтвердите запрос прав администратора.
Это консольный мастер: выберите «Установить агент», укажите путь к профилю и каталог
наблюдения. После завершения окно остаётся открытым до нажатия Enter.

По умолчанию наблюдаются `/home` или `C:\Users`, включено только обнаружение.
Автоматический карантин включается отдельным выбором. Мастер показывает итоговые
параметры до установки. После загрузки и проверки базы он регистрирует агент,
настраивает автозапуск и ждёт подтверждения запуска наблюдения.

Автоматизированная установка:

```sh
sudo ./install.sh agent --profile /secure/enrollment.json --watch /home --yes
```

В PowerShell от администратора:

```powershell
.\SpireSetup.exe agent --profile C:\Secure\enrollment.json --watch C:\Users --yes
```

Для нескольких каталогов повторите `--watch`. Для карантина добавьте
`--policy quarantine`. Профиль содержит enrollment token: передавайте его по
защищённому каналу. В нём нет admin token, ключа подписи feed или закрытого TLS-ключа.

## Первичная настройка сервера

Подготовьте DNS-имя сервера, TLS-сертификат с цепочкой и соответствующий PEM-ключ,
публичный ключ подписи feed и готовую подписанную базу. Выпуск базы описан в
[инструкции по подписанным обновлениям](signed-updates-and-response.md).
Закрытый **ключ подписи feed** остаётся у выпускающего обновления администратора.
Мастер проверяет подпись, срок действия, содержимое SQLite и YARA перед публикацией.
Он не выпускает фиктивную «защитную» базу и не отключает проверку TLS.

```sh
sudo ./install.sh server \
  --public-url https://edr.example.org \
  --tls-cert /secure/fullchain.pem --tls-key /secure/tls-key.pem \
  --public-key /secure/feed-public.hex --feed /secure/release-1 --yes
```

В Windows те же параметры передаются `SpireSetup.exe server`. Для частного CA
добавьте `--ca-cert /secure/ca.pem`: публичный CA попадёт в профиль, агент использует
его для API и feed. Системное хранилище сертификатов не изменяется.
HTTP разрешён только на loopback, например `http://127.0.0.1:8080`, для локального
тестирования. Порт берётся из URL: без явного порта HTTPS использует 443, HTTP — 80.
Настройку DNS и входящего порта firewall выполняет администратор инфраструктуры.

Мастер создаёт два независимых случайных токена и сохраняет:

| Файл в каталоге настроек сервера | Назначение |
| --- | --- |
| `admin-credentials.json` | URL консоли и admin token для администратора |
| `enrollment.json` | Профиль подключения клиентских машин |
| `secrets.json` | Сохранённые токены для повторной установки |

Консоль доступна по `/console`. Мастер проверяет `/health` после запуска сервера.
Токены не выводятся в итоговый план. Повторный запуск с тем же адресом и ключом
сохраняет токены, SQLite, очередь событий, карантин и identity агента; изменяемые
текстовые конфиги получают одну резервную копию `.previous`. Настройки мастера
(каталоги и режим реагирования) применяются заново: передавайте нужные значения
при переустановке. Две параллельные установки блокируются системной блокировкой.

Служба останавливается на время замены файлов. При сбое она может остаться
остановленной: исправьте указанную ошибку и повторите установку, затем запустите
`doctor`. Это восстановление повторным запуском, автоматического отката бинарников
нет. Автоматическая смена сервера/публичного ключа запрещена, чтобы не смешивать
существующую identity с другим сервером. Старые ручные установки требуют отдельной
миграции; мастер откажется перезаписывать чужую службу или конфигурацию.

## Файлы, автозапуск и диагностика

| | Linux | Windows |
| --- | --- | --- |
| Программа | `/opt/spire` | `%ProgramFiles%\Spire` |
| Настройки | `/etc/spire/{agent,server}` | `%ProgramData%\Spire\config\{agent,server}` |
| Данные | `/var/lib/spire/{agent,server}` | `%ProgramData%\Spire\data\{agent,server}` |
| Автозапуск | `spire-agent.service`, `spire-server.service` | `SpireAgent`, `SpireServer` в Планировщике заданий |
| Журнал | `journalctl -u spire-agent` / `spire-server` | `service.log` в каталоге данных роли |

Linux-сервер запускается под отдельным `spire-server`, агент — root.
Обе службы имеют лимит памяти 768 MiB; агент также ограничен CPUQuota=100%.
Сервер может писать только в свой каталог данных в рамках systemd sandbox.

Windows использует задачи SYSTEM при загрузке ОС, без ограничения длительности
сеанса. PowerShell-супервизор перезапускает дочерний процесс, ограничивает журналы
примерно 10 MiB плюс одна предыдущая копия. Windows Job Object ограничивает группу
1 GiB памяти и 64 процессами и завершает дочерние процессы при остановке задачи.
Каталоги защищены ACL для SYSTEM и Administrators. Это ещё не SCM-служба и не MSI;
управление выполняется через Планировщик. Для этой версии нужен Windows 10/11 или
Server 2019+ x64 с Windows PowerShell 5.1 и доступным Add-Type (FullLanguage).
Windows-инвентаризация процессов пока не реализована; установка не добавляет эту
возможность движку.

```sh
sudo ./install.sh doctor --role agent
sudo ./install.sh doctor --role server
sudo spire check-feed
```

```powershell
.\SpireSetup.exe doctor --role agent
.\SpireSetup.exe doctor --role server
& "$env:ProgramData\Spire\config\agent\spire.ps1" check-feed
```

`doctor` проверяет службу/задачу, активную подписанную базу агента и авторизованный
доступ к API. На Linux CLI-обёртка `spire` подключает настройки установленного
агента. В Windows аналогичную роль выполняет `spire.ps1`, запускаемый администратором.

## Проверка без установки на машину

`--dry-run` проверяет входные файлы и показывает план без записи и запуска служб.
`--stage PATH` создаёт дерево файлов внутри PATH; не запускает сеть, бинарники,
установку Python или службы. **Stage не подтверждает корректность подписи feed,
подключение или работоспособность установки.** Это режим проверки упаковки.

Из исходников (Python 3.12+ нужен для тестов и упаковки):

```sh
cargo build --release --locked -p spire -p spired -p av_core
python3 -B installer/setup.py agent --bin-dir target/release \
  --profile /secure/enrollment.json --stage /tmp/spire-image --yes
python3 -B -m unittest discover -s installer/tests -v
```

`SPIRE_CONFIG_PATH` задаёт JSON-конфиг ядра; `SPIRE_AGENT_CONFIG` — TOML агента;
`SPIRE_STATE_DIR` — identity и карантин; `SPIRE_CA_CERT` — дополнительный доверенный
CA. `SPIRE_READY_FILE` используется мастером для подтверждения запуска watcher.
Если явно заданный конфиг отсутствует, агент/CLI завершаются с ошибкой.

## Сборка дистрибутивов

На каждой целевой ОС соберите Rust-бинарники и установите инструменты упаковки:

```sh
python -m pip install uv==0.12.7 pyinstaller==6.22.3
cargo build --release --locked -p spire -p spired -p av_core
python -B installer/package.py
```

Windows-бинарники собираются нативно на Windows; CI добавляет
`RUSTFLAGS=-C target-feature=+crt-static`, чтобы включить C runtime в Rust-бинарники.
Результат: `dist/spire-setup-linux-x86_64.tar.gz` или
`dist/spire-setup-windows-x86_64.zip` и файл SHA-256 рядом.
В Windows ZIP содержит `SpireSetup.exe` с запросом UAC. Архив включает только
разрешённые исходники сервера, нативные программы, uv, мастер и документацию.
БД, профили, `.env`, приватные ключи и тестовые данные из рабочего дерева не копируются.

Workflow **Client installers** запускается вручную, для тегов `v*` и релевантных PR.
Он собирает обе платформы, выполняет тесты, проверяет реальную регистрацию агента
и доставку обнаружения на временный сервер, затем сохраняет архивы в artifacts.
Windows job lifetime проверяется отдельным нативным тестом. Публикации релиза нет.
Linux CI собирает на Ubuntu 22.04; для клиентов нужны совместимые glibc/OpenSSL 3.
Локальная сборка наследует минимальные версии библиотек машины сборки.

`bundle.json` и SHA-256 обнаруживают повреждение файлов, но не удостоверяют
издателя установщика. Получайте архив из доверенного канала. Для коммерческого
распространения ещё требуется настроить подпись Windows executable (Authenticode)
и релизных архивов; ключей издателя в проекте нет. Подпись базы Ed25519 уже проверяется
независимо от этого. Обновления самих бинарников пока выполняются повторным запуском
мастера; ежедневная публикация feed и обновление работающего агента остаются отдельным
операционным процессом.

Справочные спецификации реализации: [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects),
[Task execution time limit](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-executiontimelimit-settingstype-element),
[PyInstaller usage](https://www.pyinstaller.org/en/stable/usage.html).
