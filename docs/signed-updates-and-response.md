# Обнаружение, реагирование и подписанные обновления

## Поведение

`SpireAvScanner` читает файлы и возвращает результаты. Он не перемещает файлы и не показывает уведомления. Результат обнаружения содержит SHA-256 фактически прочитанных данных. `response::respond` применяет отдельную политику и возвращает `skipped`, `succeeded` или `failed`; ошибка действия не заменяет обнаружение.

По умолчанию действует `observe`. Для CLI карантин включается явно:

```bash
spire scan fast --path /path/to/check
spire scan --quarantine fast --path /path/to/check
spire scan yara-scan --path /path/to/check
```

Для демона в `~/.config/spire/Config.toml` задаётся `response_policy = "quarantine"` (по умолчанию `"observe"`). Удалённая команда `scan_path` остаётся только диагностической и возвращает `response_policy: "observe"`, `complete` и список ошибок. При превышении лимита результатов ответ команды помечается `truncated`.

Телеметрия обнаружения больше не утверждает, что карантин выполнен. Результат действия отправляется отдельным `response_result`, с путём и SHA-256. Перед удалением оригинала карантин сверяет хеш сохранённой копии с обнаружением. Это снижает риск применения старого вердикта к новому содержимому, но не заменяет будущую защиту файловых операций от всех гонок TOCTOU.

## Новый формат обновлений

Пакет состоит из четырёх файлов:

- `manifest.json`: schema_version=1, монотонная version, expires_at (Unix UTC), размеры и SHA-256 базы и архива;
- `manifest.sig`: 64 байта подписи Ed25519 **точных байтов manifest.json**;
- `database.db`: SQLite с непустой таблицей `default_db(md5hash, sha256hash, name)`;
- `yara.zip`: только `.yar`/`.yara`, без симлинков и выходов за каталог.

Оба хеш-поля таблицы должны содержать строки (можно пустую строку для неизвестного хеша). Рекомендуются индексы по md5hash и sha256hash. YARA-файлы действительно загружаются и компилируются; `include` отключён, чтобы компиляция не читала неподписанные файлы вне пакета. Старые наборы правил с include нужно подготовить к этому формату.

Публичный ключ задаётся на endpoint вручную или доверенным установщиком. Из update-сервера ключ не загружается. Закрытый ключ остаётся у сборщика релизов.

## Выпуск пакета

Сборка инструментов:

```bash
cargo build --release --locked
```

Создать пару ключей один раз на машине выпуска (родительские каталоги должны существовать):

```bash
./target/release/spire-feed keygen \
  --private-key ./feed-private.pk8 \
  --public-key ./feed-public.hex
```

Закрытый ключ записывается в PKCS#8 с правами 0600 на Unix. Инструмент отказывается перезаписывать существующие ключи. На Windows доступ к ключу следует ограничить ACL до запуска инструмента. Эти команды здесь не выполнялись с production-ключами.

Подписать подготовленные базу и архив; пример срока — 30 дней:

```bash
./target/release/spire-feed sign \
  --private-key ./feed-private.pk8 \
  --database ./database.db \
  --yara ./yara.zip \
  --version 1 \
  --expires-at "$(python3 -c 'import time; print(int(time.time()) + 30*86400)')" \
  --out ./release-1
```

Каталог `--out` должен быть новым. Публикуйте весь готовый каталог. Подписывающий инструмент подписывает содержимое; структурная проверка SQLite и компиляция YARA выполняются установщиком до активации. В release pipeline запускайте сквозную проверку перед публикацией.

Сервер раздаёт эти файлы из `SPIRE_UPDATES_DIR`. Например, укажите абсолютный путь к `release-1` и запустите сервер по `server/README.md`. Для подключения с других хостов нужен HTTPS. HTTP разрешён только на loopback, редиректы отключены.

## Конфигурация endpoint и установка

В рабочем каталоге CLI/демона создайте `config.json`:

```json
{
  "spire_dir": "/var/lib/spire",
  "update_url": "https://updates.example.org",
  "update_public_key": "ВСТАВЬТЕ_64_HEX_СИМВОЛА_ИЗ_feed-public.hex",
  "scan_limits": {
    "max_file_bytes": 67108864,
    "max_files": 10000,
    "max_entries": 50000,
    "max_depth": 64,
    "timeout_secs": 120,
    "yara_timeout_secs": 2
  }
}
```

Для непривилегированного запуска выберите доступный пользователю `spire_dir`. Обновление:

```bash
spire update-db
# Либо явно задать доверенный адрес (публичный ключ остаётся из config.json):
spire update-db --url https://updates.example.org
```

После обновления перезапустите работающий агент: открытая БД и пути сенсора относятся к версии, загруженной при старте. Hot reload в этот этап не входит.

Установщик ограничивает загрузки и распаковку, проверяет подпись, срок, возрастающую версию, размеры, хеши, структуру базы и компиляцию правил. Затем SQLite-транзакция переключает указатель на целиком подготовленный каталог `feeds/signed-*`. Ошибка до активации оставляет предыдущую версию активной. База сигнатур открывается только для чтения.

Повтор той же версии и меньшая версия отклоняются. Для исправления неудачного релиза выпускайте пакет с **новым большим номером**, даже если возвращаете старое содержимое. Не удаляйте `feed-state.db`: в нём хранится граница защиты от отката. Истёкший manifest отклоняется при установке и запуске; уже работающий процесс не перепроверяет срок непрерывно.

## Совместимость и карантин

Неподписанные загрузки больше не поддерживаются. Если нет доверенного ключа или валидного установленного пакета, агент не запускается с пустой базой и не выдаёт её отсутствие за чистые файлы. Сначала подготовьте и установите подписанный пакет.

Карантин теперь хранит записи в `spire_dir/response.db`, отдельно от подписанных сигнатур. Записи из прежнего `spire_dir/db_path` (по умолчанию `database.db`) переносятся один раз с сохранением ID. При конфликте ID миграция завершается ошибкой, а не перезаписывает записи. Старая база не удаляется. Команды `quarantine list/restore/delete` доступны без загрузки подписанного feed.

Если раньше использовался нестандартный путь базы, сохраните `db_path` в `config.json` на время миграции. Не копируйте legacy quarantine-таблицу в публичный пакет обновлений.

## Лимиты

| Область | Значение по умолчанию |
|---|---|
| Читаемый файл | 64 MiB; превышение становится ошибкой сканирования |
| Один обход | 10 000 результатов, 50 000 записей ФС, глубина 64 |
| Время обхода / одного YARA-сканирования | 120 с / 2 с |
| YARA-компиляция | 4096 записей, 1 MiB на файл, 16 MiB суммарно; проверка времени между файлами |
| Буфер notify | 1024 события; потери учитываются в agent_status |
| Очередь телеметрии | 10 000 событий / 32 MiB JSON / 256 KiB на событие |
| Пакет отправки | до 100 событий и 512 KiB JSON полезной нагрузки |
| SQLite агента | 128 MiB основной БД; WAL checkpoint каждые 128 страниц |
| Журнал команд | 10 000 ID, результат до 256 KiB |
| Update DB / ZIP / распакованные правила | 128 / 16 / 16 MiB |
| Каталог версий feed | 512 MiB и 20 000 записей |
| Карантин | до 4096 объектов и 1 GiB, до 256 MiB на объект |
| HTTP API | тело до 2 MiB, до 16 одновременных запросов, 10 с на получение тела |
| systemd-профиль агента | MemoryHigh=384M, MemoryMax=512M, CPUQuota=100%, TasksMax=64 |

10% очереди резервируются под приоритетные события. Обнаружения/результаты действий отправляются первыми и могут вытеснять старые низкоприоритетные события. Когда очередь заполнена только приоритетными событиями, новое событие отклоняется с ошибкой и увеличением `queue_dropped`; бесконечное хранение офлайн не обещается. Переполнение очереди не завершает сетевой worker. Повреждённые и слишком большие старые записи удаляются с учётом потерь, чтобы не блокировать доставку остальных событий. Счётчик передаётся в heartbeat после восстановления доступной ёмкости.

Параметры очереди можно задать в `[queue_limits]` агентского `Config.toml`: `max_events`, `max_payload_bytes`, `max_event_bytes`, `max_db_bytes`, `max_commands`. Значения проверяются по верхним границам. Основная БД ограничивается SQLite max_page_count; WAL/временные файлы и SQLite overhead нужно учитывать отдельно. Понижение лимита ниже уже существующей БД требует обслуживания; старые события автоматически не удаляются при открытии.

Журнал команд не очищается автоматически, чтобы не потерять защиту от повторного выполнения. При достижении квоты новые действия отклоняются. Старые версии feed также не удаляются автоматически: перед освобождением места убедитесь, что они не используются запущенными агентами. Незавершённые staging-каталоги после аварии учитываются в квоте.

Лимиты времени в обходе/компиляции проверяются между операциями и не прерывают зависший системный I/O. Жёсткие ограничения памяти и CPU доступны в приложенном systemd unit; Windows job objects пока не реализованы. Для unit создайте `/etc/spire/config.json` и настройте агентский TOML сервисного пользователя. Лимиты HTTP ограничивают входящие запросы, но не заменяют политику ретенции серверной БД.

## Проверка

```bash
cargo test --workspace --locked
cargo build --workspace --locked
PYTHONPATH=server/src server/.venv/bin/python -m unittest discover -s server/tests -v
python3 tests/e2e_signed_feed.py
```

Сквозной тест создаёт временные ключи и файлы, запускает HTTP только на localhost и проверяет цепочку подпись → загрузка → активация → hash/YARA-детекция, а также отказ при подмене и повторе версии. Он не требует внешней сети и не меняет настройки установленных агентов.
